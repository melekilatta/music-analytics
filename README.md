# Music analytics

Прототип прогнозно-аналитической системы для ежедневного анализа музыкальных треков и новых релизов. Система собирает открытые данные Deezer и Spotify, ведёт типизированный исторический слой, проверяет качество данных и формирует витрины для предметного и операционного дашбордов, а также для последующего прогнозирования.

## Задача и пользователи

Предметный пользователь — музыкальный аналитик или менеджер лейбла, которому нужно видеть динамику популярности треков, позиции в чартах, новые релизы и их первые результаты. Операционный пользователь — владелец конвейера данных, который контролирует успешность загрузок, полноту слоёв и результаты проверок качества.

Ключевой временной показатель для следующего этапа прогнозирования — дневная популярность трека Spotify (`spotify_popularity`). Для чартового контура также доступна целевая переменная `chart_position`; положительное значение `chart_position_delta_1d` означает улучшение позиции по сравнению с предыдущим календарным днём.

## Архитектура

```text
Deezer API (чарты, треки, артисты) ─┐
                                     ├─> bronze.raw_response
Spotify API (треки, артисты, альбомы)┘          │
                                                 ▼
                    silver.dz_* / silver.sp_* — типы, очистка, дедупликация
                                                 │
                                                 ▼
                   gold.bridge_track_mapping_snapshot
                                                 │
          ┌──────────────────────────────────────┼─────────────────────────────────────┐
          ▼                                      ▼                                     ▼
gold.fact_track_daily              gold.fact_chart_position_daily    gold.fact_release_track_daily
          │                                      │                                     │
          └─────────────────────────> gold.mart_music_daily <─────────────────────────┘
                                                 │
                                                 ▼
                                      предметный дашборд / ML

bronze + silver + meta.dq_results ────────────> gold.mart_pipeline_daily
                                                 │
                                                 ▼
                                       операционный дашборд
```

`Bronze` хранит исходные JSON-ответы API с датой снимка и `run_id`. `Silver` — типизированные ежедневные снимки без небезопасных преобразований. `Gold` содержит бизнес-гранулярность, заранее рассчитанные KPI и исторический snapshot сопоставления Deezer–Spotify. Gold строится только после прохождения error-проверок DQ для соответствующей даты.

## Источники и инкрементальность

Deezer и Spotify — разнородные REST API. Сборщик получает общий или жанровые чарты Deezer, детали треков и артистов, затем сопоставляет Deezer-треки с Spotify по ISRC. Также отдельно отслеживаются новые релизы уже известных Spotify-артистов: это контрольная группа, не ограниченная попаданием в чарт.

В Bronze действует первичный ключ `(source, entity_type, entity_id, snapshot_date)`, а в Silver и Gold — ключи с датой и идентификатором сущности. Поэтому повторный запуск безопасен: новые данные добавляются, существующие снимки обновляются без дублирования. Журнал `meta.ingestion_log` сохраняет результаты каждого запуска.

## Подготовка и запуск

Нужны Docker/Docker Compose, Python 3.10+ и Spotify Client Credentials. Создайте файл `.env` на основе `.env.example`, укажите безопасный пароль PostgreSQL и ключи Spotify.

```powershell
Copy-Item .env.example .env
# отредактируйте .env
python -m pip install -r requirements.txt

docker compose up -d
python src\collect.py
python src\run_silver.py
python src\run_gold.py
```

Для типового ежедневного запуска достаточно выполнять команды в показанном порядке. `run_silver.py` и `run_gold.py` создают или обновляют необходимые SQL-объекты самостоятельно, поэтому добавление новых Gold-таблиц не требует удаления существующего Docker volume.

Полезные варианты:

```powershell
# Пересчитать Silver с заданной даты и выполнить DQ последней даты Bronze
python src\run_silver.py --from 2026-10-01

# Выполнить базовые DQ за конкретную дату
python src\run_silver.py --date 2026-10-24

# Пересчитать Gold только за одну дату
python src\run_gold.py --date 2026-10-24

# Backfill Gold с даты до последнего доступного Silver-снимка.
# Для каждой даты будет выполнен базовый DQ quality gate.
python src\run_gold.py --from 2026-10-01
```

Если `run_gold.py` сообщает о не пройденном quality gate, это ожидаемое защитное поведение: сначала нужно исправить проблему источника или Silver, затем повторить запуск. Предупреждения (`warn`) не блокируют Gold, но отображаются в операционной витрине.

## Gold-слой

| Объект | Гранулярность | Назначение |
|---|---|---|
| `gold.bridge_track_mapping_snapshot` | дата × Deezer-трек | Фиксирует сопоставление Deezer → Spotify на момент расчёта; не переписывает исторические связи задним числом. |
| `gold.fact_track_daily` | дата × Spotify-трек | Каноническая ежедневная витрина популярности трека, исполнителя и альбома. Несколько Deezer-версий одного Spotify-трека сначала агрегируются, поэтому Spotify-popularity не дублируется. |
| `gold.fact_chart_position_daily` | дата × жанр × Deezer-трек | Детали общих и жанровых чартов, дневное изменение позиции и доступное сопоставление со Spotify. |
| `gold.fact_release_track_daily` | дата × Spotify-альбом × Spotify-трек | Контрольная группа новых релизов, включая треки, которых нет в Deezer-чартах. |
| `gold.mart_music_daily` | дата | Готовые KPI предметного дашборда: объём наблюдаемой выборки, средняя/медианная popularity, лидер дня, покрытие чартов и новые релизы. |
| `gold.mart_pipeline_daily` | дата | Операционные KPI: запуски, запросы, ошибки, объёмы Bronze/Silver/Gold и статусы DQ. |

Ключевое проектное решение — не объединять чарт с канонической витриной треков «один к одному». Один Deezer-трек может появляться в нескольких чартах, а несколько Deezer-версий (например, ремастер и оригинал) могут соответствовать одному Spotify-треку. Поэтому чарт и трековая аналитика имеют разные факт-таблицы, а в `fact_track_daily` Deezer-часть предварительно агрегирована.

## Контроль качества и происхождение данных

Базовые проверки находятся в `sql/dq/10_dq.sql`: полнота обязательных API-полей, типы, диапазоны, допустимость значений, сверка Bronze → Silver, ссылочная целостность, уникальность каталога, свежесть и непрерывность ряда. Gold добавляет проверки в `sql/dq/20_gold_dq.sql`: полноту Gold-фактов относительно Silver, диапазоны бизнес-метрик, связь чартов со Spotify-снимками, уникальность bridge и согласованность KPI с фактом.

Все результаты записываются в `meta.dq_results`. Прослеживаемость показателя, например `gold.fact_track_daily.spotify_popularity`, выглядит так: предметный дашборд → Gold-витрина → `silver.sp_track_daily.popularity` → `bronze.raw_response.payload.popularity` → Spotify API и `meta.ingestion_log.run_id`. Для строк Gold дополнительно сохраняются `*_bronze_run_id`.

## Подключение дашбордов

Предметный дашборд следует строить на `gold.mart_music_daily` и детализировать данными `gold.fact_track_daily`, `gold.fact_chart_position_daily` и `gold.fact_release_track_daily`. Вопросы, на которые он отвечает: как меняется средняя популярность, какие треки лидируют, что происходит в конкретном жанре, насколько новые релизы успешны в первые дни и как связаны изменения позиций с популярностью Spotify.

Операционный дашборд строится на `gold.mart_pipeline_daily` и `meta.dq_results`. Его вопросы: все ли загрузки завершились успешно, сколько запросов завершилось ошибкой, на каком слое возникла проблема, за какую дату есть DQ-fail и каков объём данных в каждом слое. Для фильтров используйте `snapshot_date`, `genre_id`, `spotify_artist_id`, `spotify_album_id` и `is_new_release_track`.

## Интерактивные дашборды

Дашборд реализован на Streamlit и содержит две панели, которые требуются методичкой. Он читает только Gold- и DQ-слои PostgreSQL, не изменяя их. После установки новых зависимостей запустите:

```powershell
python -m pip install -r requirements.txt
streamlit run dashboard\app.py
```

В браузере откроется локальный адрес, обычно `http://localhost:8501`. Предметная панель показывает динамику средней и медианной popularity, лидеров Spotify, позиции Deezer-чарта с фильтром жанра, а также результаты новых релизов. Операционная панель показывает объёмы Bronze/Silver/Gold, нагрузку API, число ошибок и журнал DQ с выгрузкой CSV.

## Прогнозный контур: следующий этап

`gold.fact_track_daily` уже содержит временной ряд `spotify_popularity`, лаговую динамику `popularity_delta_1d`, атрибуты артиста и альбома, возраст релиза и агрегированные признаки Deezer. Для честной валидации нужно разделять train/test по времени, не перемешивая будущие даты в обучении. Базовую модель можно сравнить с моделью «значение popularity вчера», а вторую модель построить с лагами popularity, изменением позиции в чарте и возрастом релиза. Для прогноза позиции используйте отдельный ряд `gold.fact_chart_position_daily`, не смешивая жанровые строки с канонической трековой гранулярностью.
